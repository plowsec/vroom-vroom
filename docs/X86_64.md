# Experimental x86-64 Linux support

The native x86-64 board uses Linux KVM. It does not translate ARM guests:
use x64 Windows media or amd64 Linux images on an x86-64 host.

The implementation includes reset-vector OVMF boot, direct bzImage boot,
low RAM below 3 GiB and additional RAM above 4 GiB, ACPI (FADT, FACS, MADT,
DSDT, MCFG and optional TPM2), PCI configuration ports and ECAM, COM1 at
0x3f8/IRQ4, CMOS memory reporting/UTC clock, PM timer, reset and shutdown.
KVM supplies PIC, IOAPIC, LAPIC, PIT and INIT/SIPI startup. Devices use PCI;
`virtio_transport = "mmio"` is rejected. USB input comes from the existing
xHCI controller. Firmware-facing PIIX registers are fixed at the board's
addresses; this is not a complete PIIX chipset emulation.

The upstream [direct Linux reference profile](../crates/vmm/X64_LINUX.md)
remains separate: direct kernel boot with automatic transport selects its
checked one-CPU/512-MiB loader and cold-boot-only lifecycle. Set
`virtio_transport = "pci"` for direct boot on the experimental full PC board.
Linux/Windows UEFI guests also use the full PC board described here,
including reset, snapshots and research debugging. `os = "other"` UEFI
configs retain the upstream [firmware preflight](../crates/vmm/X64_FIRMWARE.md)
and do not execute; use `os = "linux"` or `os = "windows"` for the full board.
Secure Boot is rejected on both x64 profiles. Isolated SMM prerequisites use
a separate restricted CPU path, without snapshot/debugger access.

## Requirements

- An x86-64 Linux host with read/write access to `/dev/kvm`.
- OVMF CODE and a matching initialized VARS template, in the 2 or 4 MiB
  format. Common distro locations are detected. Explicit `boot.firmware`
  selects CODE; `boot.vars` names the per-VM writable copy. An existing
  ARM variable store must not be reused.
- `7z`, `mformat`, `mcopy` and `wimlib-imagex` for Windows install media
  on Linux. wimlib splits large install images and configures WinPE to
  start Setup explicitly with its unattended answer file.
- Building guest tools also requires cargo-xwin, the native Linux musl
  toolchain, and `sfdisk` (util-linux).

Build tools with `sh scripts/make-guest-tools.sh`. On Linux this builds the
native musl agent and native Windows agent, extracts the matching virtio
drivers, and creates an MBR/FAT32 image without mounts or root. The Windows
answer file and setup script select `amd64` drivers on x64. The Ubuntu
ready-made image download also selects amd64 on x86-64.

For an existing UEFI config, point its disks at native guest images and
give it a fresh `boot.vars` path. The usual CLI can create a Windows VM:

```sh
cargo build -p vroom-cli
target/debug/vroom new win64 --os windows --ready --iso /path/to/Win11_x64.iso
```

Existing installations must already use UEFI boot; legacy BIOS/MBR
Windows installations without an EFI boot partition do not boot unchanged.
Vroom does not currently provide a legacy BIOS firmware path.

To test an existing QCOW2 without changing it, create a disposable overlay
and configure that overlay as the writable disk. If the backing image is
in another directory, explicitly allow it (backing files are opened read-only):

```toml
[[disk]]
path = "/tmp/test/overlay.qcow2"
format = "qcow2"
bus = "nvme"
backing_dirs = ["/path/to/source-images"]
```

Stop any other VM using the source image while testing. Use separate
firmware variables and state directories too.

## Validation and limits

Software tests cover RAM holes, linked ACPI checksums, bzImage boot params
and page tables, serial loopback/interrupt IDs, fw_cfg PIO/DMA endianness,
PCI config byte lanes, flash programming/erase, CMOS/power ports, and
agreement between legacy and extended FADT power-register descriptions.
The Linux media test packages a synthetic ISO and reads its answer file
back from the resulting FAT partition:

```sh
cargo test -p vroom-arch -p vroom-devices -p vroom-hv -p vroom-vmm -p vroom-tools --lib
cargo test -p vroom-tools linux_install_stick_end_to_end -- --ignored
```

The hardware smoke test runs reset-vector instructions through KVM,
checks port reads/writes and CPU/irqchip save/restore:

```sh
cargo test -p vroom-hv --test x86_64 -- --ignored
```

The reset-vector KVM test and a full OVMF
EFI-application boot have passed on an Intel i7-12700H Linux host. The EFI
test uses two vCPUs, checks ACPI checksums, CPU entries, extended FADT
power registers and EFI GetTime, boots from
NVMe/FAT, writes a serial success marker, and powers off with the VMM's
sandbox enabled. Reproduce it with:

```sh
sh scripts/smoke-x86-uefi.sh
```

It needs clang, lld-link, mtools and sfdisk, and creates only temporary
media. `VROOM_SMOKE_CPUS=1` or `4` changes the CPU count. Host KVM access is
required: a restricted execution environment can hide `/dev/kvm` even
when the host's KVM modules are loaded.

`VROOM_SMOKE_MEMORY_MIB=4096` also exercises RAM above the 3 GiB PCI hole.
Both two-vCPU/512-MiB and four-vCPU/4-GiB configurations have passed.

An existing BIOS/MBR Windows QCOW2 has also been tested through a writable
overlay with two vCPUs and 4 GiB RAM, networking disabled and the VMM
sandbox enabled. OVMF detects its NVMe disk but reports no bootable
device, as expected without EFI boot files. This is not a Windows boot
validation. The source image's size, modification time and change time
remained unchanged.

Windows 11 x64 boot files extracted from an ISO now boot through WinPE
to the graphical Setup interface with four vCPUs and 4 GiB RAM. This
boot-only medium deliberately omits the large install image, so Setup's
missing-media/driver prompt is expected (and is also seen in the QEMU
control test). A subsequent test packaged the complete ISO as a FAT32
installer, splitting its greater-than-4-GiB WIM into SWM parts. With all
installation files present, Setup reaches its normal language-selection
screen without the missing-media prompt, using four vCPUs, 4 GiB RAM,
virtio 2D graphics and a disposable NVMe target. The copied SWM parts
and critical boot/setup files were hash-verified against the staging
files.

A fresh **Windows 11 Pro build 26300 (AMD64)** installation has since
completed on a new 64 GiB QCOW2 disk. Validation reached the desktop,
executed PowerShell over emulated USB keyboard input, confirmed the
edition/architecture and NVMe disks, then shut Windows down cleanly.
With the installer and answer disks detached, a cold boot returned to
the desktop and reported only the 64 GiB system disk. The VMM exited
normally after a second Windows shutdown, with its sandbox enabled.

This validation used an offline local test account and the existing
answer file's TPM/Secure Boot hardware-check bypasses. Activation,
networking and guest-tools integration were not part of this test.

The Linux install-media builder now embeds an explicit unattended
WinPE startup in the WIM's bootable image; fixed NVMe answer media is
not reliably auto-discovered by newer Setup builds. Generated FAT media
uses distinct, nonzero MBR disk signatures (avoiding Windows disk-ID
collisions), and private file permissions because it can hold credentials.

Viewer-enabled shutdown also exposed an AF_UNIX self-connect blocked
by seccomp. The display listener now uses a pre-opened wake channel;
accepting pre-opened viewer/control listeners is allowed while new Unix
connections, binds and listeners remain prohibited. Regression tests
exercise both the allowed IPC and forbidden new-connection cases.

Windows testing exposed two pre-Setup blockers that a basic EFI
application did not exercise:

- The RTC's read-only status register D accepted OVMF's initialization
  write, clearing its valid-clock bit. EFI GetTime then returned
  EFI_DEVICE_ERROR and Windows stopped with
  `BlInitializeLibrary failed 0xc0000185`. Status C/D writes are now
  ignored, and the hardware smoke test explicitly checks GetTime.
- The revision-6 FADT populated legacy PM port addresses but left the
  extended GAS fields zero. Windows' HAL consumes the extended fields
  for modern revisions and stopped with bugcheck 0x5c/0x8200 in ACPI PM
  register initialization. Both descriptions now name the same ports.

Hardware testing caught regressions beyond compilation: VMX-only MSRs
must be excluded from snapshots when VMX is disabled; older OVMF builds
need one contiguous low-RAM fw_cfg record; PCI's 64-bit aperture must match
firmware allocation; absent devices must return all ones; and the flash
clear-status response must match OVMF's detection sequence. The direct
Linux E820 map still excludes legacy memory holes.

The optional `vroom-lab` now has a Linux AMD64 backend and a private JSON-RPC
agent socket. It supports all-CPU pause, snapshot/restore, memory/register
access, four shared hardware breakpoint/watchpoint slots, single-step, Windows
kernel discovery, exact-build PDBs, and process/module inspection. Its x64
command list excludes ARM-only tracing and fuzzing. A live test from a Coop VM verified ntoskrnl,
the enrolled Falcon driver, process/module lists, a hardware breakpoint and
single-step without patching Windows code. The backend lives on the KVM host;
Coop only needs the RPC client and an SSH reverse socket tunnel. See
[the kernel agent reference](../research/README.md#linux-amd64-backend).

Nested x86 virtualization, AVX/XSAVE guest features, RTC periodic/alarm
interrupts, PS/2 keyboard/mouse input, suspend-to-RAM, and Windows 3D wrapper
builds on Linux are not implemented. Use virtio 2D graphics. Existing ARM
boards and macOS guest-tools packaging retain their existing paths.

Implementation references: the [KVM API](https://docs.kernel.org/virt/kvm/api.html)
defines the in-kernel interrupt controllers, PIT and CPU state operations;
the [QEMU fw_cfg specification](https://www.qemu.org/docs/master/specs/fw_cfg.html)
defines x86 port layout and DMA byte order.
